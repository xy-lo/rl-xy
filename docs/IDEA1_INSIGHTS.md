# Idea1：关键路径瓶颈与下一步实验

分析基于 4B/8B/14B 各 1,536 条完整 test1 的原生事件和冻结工作量。当前完整 Idea1 为 108.836/186.396/276.267 秒；相对仅生成协作，4B 退化 1.13%、8B 改善 0.33%、14B 改善 3.28%。8B/14B 仍慢于 GPU 条件模型。分析区分实际运行、回溯约束推算和待实现策略。

## 1. 优化目标已经从生成长尾转向下游释放时间

三档生成持续 53.219/103.942/156.108 秒，旧策略与 reference 准备分别从 45.557/84.844/124.203 秒开始。但真正提前开始反向的训练组只有 2/27、2/27、3/27。大量“提前工作”是策略准备，不能全部计作梯度训练。

**空闲的大部分已发生在生成之后。** 总动态空闲积分分别为 1,763.454/2,466.837/3,233.068 die·s，其中生成后占 93.26%/85.07%/86.00%。因此，继续只缩短最后几个 decode 请求，不会自动消除最大的资源浪费。需要度量每个动作对最终更新关键路径的影响，而不只看生成完成时间或角色占用率。

## 2. 样本已 EOS，不等于训练消费者已拿到数据

| 模型 | 关键组全部样本 EOS / s | 本域释放约 / s | 关键组实际开始准备 / s | 释放后额外等待 / s | 最后提供者状态 |
|---|---:|---:|---:|---:|---|
| 4B | 46.030 | 53.233 | 54.444 | 1.211 | 组3在策略计算微批内 |
| 8B | 55.251 | 103.098 | 103.358 | 0.260 | 组6在策略计算微批内 |
| 14B | 85.008 | 133.395 | 146.804 | 13.409 | 组21持有 helper 租约 |

三档最后一次关键样本传输本身仅约 0.186/0.370/0.868 微秒。数量级说明当前瓶颈是**服务队列和资源租约阻塞**，不是这些样本记录的带宽。已有生成收益可能被下游交付等待抵消：4B 正是提前准备的其他组占用服务边界，使关键组在全局生成结束后仍等样本。

第一项改进应是 EOS 后登记有消费者的样本，优先交付已可准入或关键路径风险高的训练组。对 helper 引入可审计的 decode 安全边界，把“长期独占整个租约”改成“允许微秒级样本服务后恢复”；策略微批同样需要服务优先级。必须模拟暂停、端点读写和网络竞争，不能直接从结果中减去等待时间。

## 3. 消除交付等待仍不足以让 8B/14B 超过 GPU

我们保留实际生成轨迹、原训练分配和每个原生批次的服务时长，仅令训练组在“本域释放且全部样本 EOS”时可用，移除交付和排队等待，再计算最后完成组。该回溯约束推算**不是新实验结果**；它忽略新样本服务对生成和通信的反作用。

| 模型 | 当前实跑 / s | 固定服务时间的就绪界限 / s | 可回收上限约 / s | 界限相对 GPU / s |
|---|---:|---:|---:|---:|
| 4B | 108.836 | 107.625 | 1.211 | −25.341 |
| 8B | 186.396 | 186.137 | 0.260 | +7.625 |
| 14B | 276.267 | 263.856 | 12.411 | +3.102 |

14B 在这一推算中关键组由 0 变为 23，说明解决一个阻塞后关键路径会转移，而不是所有等待都可线性叠加为收益。即使理想化地修复样本交付，8B/14B 仍有约 7.6/3.1 秒差距。因此不能把“修复样本传输”当作完整性能答案；它应作为可独立验证的第一项消融。

推算脚本、条件和逐组结果见[分析 JSON](../experiments/2026-11-02-idea1-joint/bottleneck-analysis.json)。它不是去掉计算/通信工作量的模拟，也不是硬件下界。

```bash
python experiments/2026-11-02-idea1-joint/analyze_bottlenecks.py --output /tmp/idea1-analysis-new
```

该命令从发布的压缩事件重算分析，要求新输出目录，保留原发布证据。发布前已核对重算 JSON 与分析文件完全相同。

## 4. 均匀分 prompt 数，并没有均匀分关键路径工作

实际每组本地批次服务时间（包含既有计算/通信计费）的均值与最大值如下：

| 模型 | 平均服务 / s | 最大服务 / s | 最大/平均 |
|---|---:|---:|---:|
| 4B | 28.083 | 54.352 | 1.94 |
| 8B | 48.671 | 82.959 | 1.70 |
| 14B | 77.249 | 129.319 | 1.67 |

三档最终关键组都是固定训练组 0。它有 8 个 prompt，而多数其他组有 7 个，但工作量差异达到 1.67–1.94 倍平均值，不能仅用 8/7 的数量差解释；实际 token 长度、策略微批形状、checkpoint 重计算和算子资源映射共同影响服务时间。更重要的是，该组的释放/交付还较晚。目标应是压低 `max(可用时间 + 剩余服务)`，而非单独平衡 prompt 数。

可检验的第二项方向是**已就绪完整 GRPO 组的任务队列**：用在线已知长度计算策略/训练成本，采用预计完成时间调度；未结束生成的真实剩余长度不能用于在线决策。先保持 TP2 与模型参数不变，避免把更换算子计时器或硬件切分带来的收益归给调度。

## 5. 训练尾部可先迁移未开始的微批，不必迁移在途梯度

当前所有训练组本轮 actor 版本相同，优化器要等全局训练结束才更新。已经完成自己任务的组仍保有 actor 和梯度缓冲。因此，优先验证的最小方案是：把其他组**尚未开始**的微批派给空闲 TP2，传递样本、old/reference logprob、advantage 等必要记录；梯度在接手组本地累加，最后统一 DP SUM 和全局归一化。

该方向可避免先实现完整训练器扩缩容、移动在途激活或部分梯度。它仍需严格保证每条轨迹训练一次、GRPO advantage 以完整组计算、不同微批大小按样本正确加权、参数版本一致、64 GB/die 容量及全部数据移动收费。这里描述的是未实现的候选，不是数值等价已验证的结论。

## 6. helper 选择需要计入下游机会成本

当前局部性评分估计 attention 协作的生成净收益，但没有给“阻塞某训练组样本交付或占住本域准入条件”定价。一个局部上有利的 helper 租约，可能让完整 step 更慢。

下一版评分应比较继续协作、短暂样本服务、释放资源这几种动作对预计最晚完成时间的影响，并限制租约长度。可先用已完成历史和当前依赖图构造保守优先级，不需要预知真实 EOS。应同时记录生成变化、关键训练组释放时间和完整 step；不能只用 die 利用率证明有效。

## 建议的实验顺序

1. **A1：样本服务优先级。** 保持当前分配/微批/算子，加入 helper 安全点与策略批次边界服务。检验关键样本等待是否下降，生成是否反而变慢，以及完整 step 的净变化。
2. **A2：未开始训练微批接管。** 先仅在生成全部结束后启用，隔离与生成竞争；记录最后 10% 工作的持续时间、空闲积分、样本唯一性、归一化与状态容量。
3. **A3：可用时间与剩余服务联合调度。** 在前两项成立后再放宽域级准入、联合调整 helper 决策，避免一次改多个机制导致归因不清。
4. **完整验证。** 冻结方法后使用 test2–4，与 GPU/H0/消融同输入配对，并补误差和硬件校准。8B 的 0.33% 单窗变化不能称稳健收益。

约 30B 扩展暂缺同源真实 trace；不能用增加模型规模来掩盖当前的依赖/负载问题。获得匹配 trace 后仍需先处理 54 die 下的合法 TP/容量，不能把 30B-A3B MoE 与稠密 32B 直接混为同一算术模型。
