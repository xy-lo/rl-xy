# H0 晶圆级 GRPO：Idea1 实验设计、实现与结果

## 1. 实验目标与整体流程

本实验研究将 GRPO 分时共置工作负载迁移到晶圆级架构后，能否利用 die 间协作减少生成长尾，并降低一次同步 RL step 的计算与通信时间。对照对象为：

1. **GPU baseline**：48 张 A100 的分时共置模拟，沿用已冻结的 test1 结果。
2. **晶圆 baseline**：H0 54 die，固定 TP2 推理组，按原同步阶段执行。
3. **晶圆 Idea1**：使用同一 H0 硬件、同一输入和相同训练策略，在生成时加入 KV 局部性感知的域内协作。

主实验的计时顺序为：**权重同步 → 生成（prefill + decode）→ 样本传输 → old policy → reference → advantage → 训练 → optimizer → 发布**。各阶段按同步屏障组合；一次 step 时间是九阶段模拟设备时间之和，不包含离线切分探索、建图、编译和仿真器主机运行时间。有效吞吐定义为全部轨迹的 **prompt token + response token 总数 / step 秒数**，不是仅输出 token 的生成速率。

本次 Idea1 **尚未接入提前训练**：它缩短生成阶段，之后八个阶段复用同模型、同输入、同策略的 54 die 晶圆 baseline 阶段结果。提前训练是原始完整构想中的后续接续机制，不能算入本轮已经得到的加速。

## 2. 模型、数据与硬件配置

### 模型和 trace

| 项目 | 设置 |
|---|---|
| 模型 | Qwen3-4B、8B、14B；Q head 分别为 32、32、40；KV head 均为 8 |
| 主实验 | test1，每模型 192 个 prompt，每个 8 条回答，共 1536 条轨迹 |
| trace | `samuki-hf/thinking-rollouts`，固定 revision `a726a001d0145eddb2d5a2f5ede60591950b141f`；DS-1000、thinking、temperature 0.6 |
| 长度 | 回答长度来自公开记录；prompt 长度根据 DS-1000 来源及模型 tokenizer 重建；输出上限 8192 token |
| 训练分组 | 192 个完整 GRPO 组分给 27 个训练组：3 组各 8 个 prompt，24 组各 7 个 prompt，保留全部回答 |

trace 回放使用已记录的长度驱动计算和通信，不在本实验中重新生成文本或评估学习效果。test1 的响应长度确实有长尾：4B、8B、14B 的 p50 分别为 2070、2325.5、1957 token，p95 分别为 8192、7948.5、6623.25 token；其中以长度上限结束的轨迹分别为 86、71、28 条。8192 是观测截断值，不能推断截断前的真实长度。

### 硬件与成本模型

| 项目 | GPU baseline | H0 晶圆 |
|---|---|---|
| 资源 | 48 × A100-SXM4-80GB，6 节点 × 8 GPU | 6×9 mesh，54 个活动计算 die；9 个六 die 协作域 |
| 本地计算 | 每 GPU 标称 BF16 稠密峰值 312 TFLOPS | 每 die 256 core，core 1 GHz，计算速率按 1.02 TFLOPS/core 的模型参数 |
| 存储容量 | 80 GB/GPU，合计 3840 GB | 64 GB DRAM/die，合计 3456 GB；每 core 1.25 MB 私有 SRAM |
| 本地内存带宽 | HBM 2.039 TB/s/GPU | 2 TB/s/die；SRAM 读/写代理分别为 400/270 GB/s/core |
| 互联 | 节点内 NVLink、节点间共享上行；详细参数见 GPU profile | 2 TB/s/边/方向的 D2D 模型，单跳 100 ns；6×9 mesh |
| 本地算子建模 | A100 实测 GEMM 与 attention 数据校准，部分集合通信实测，其他规模外推 | die/core 的算子形状、分片、私有 SRAM 与共享 DRAM 服务模型 |
| 网络 | ASTRA 原生事件和网络后端 | 同一原生后端，54 rank、6×9；数值分组 64 KiB |

按当前标称速率，54 die 总峰值约 14.100 PFLOPS、48 张 A100 约 14.976 PFLOPS；晶圆略低约 5.8%。晶圆侧 BF16 采用与 FP16 相同速率是仿真假设。GPU 本地算子有 A100 测量依据，但 48 卡端到端以及晶圆完整系统时间均为仿真，不应称为真实集群或实体晶圆实测。

### 固定切分与容量

格式为 `训练 TP / rollout TP / 训练 microbatch / log-prob microbatch / rollout 并发`：

| 模型 | GPU baseline | 54 die 晶圆 baseline 与 Idea1 |
|---|---|---|
| 4B | 4 / 4 / 16 / 16 / 128 | 2 / 2 / 4 / 8 / 32 |
| 8B | 4 / 4 / 8 / 16 / 128 | 2 / 2 / 2 / 1 / 16 |
| 14B | 8 / 8 / 8 / 16 / 128 | 2 / 2 / 1 / 1 / 16 |

GPU 方案由 tune 上的有限网格选择，是当前 best-found 方案，不宣称真实硬件全局最优。晶圆方案针对 54 die 的可执行性和 64 GB/die 容量设定；TP2 与 27 组并不表示该晶圆策略已是最优。54 个 die 均参与资源分配，不代表每一时刻都处于计算状态。

14B 在原来的训练状态、reference、梯度工作区同时常驻时，TP2 无法通过 64 GB/die 容量检查。本轮晶圆 baseline 和 Idea1 **共同**使用阶段化状态：reference 按 27 个数据并行组分片保存，在 reference 阶段执行两次 27 rank ALL_GATHER 重建，训练前释放临时副本；完整 FP32 梯度工作区仅在训练时分配。首个 step 假定 reference 已分片驻留，重建通信与端点读写纳入计时；训练阶段容量上界约 62.312 GB/die。

## 3. Idea1：KV 局部性感知的域内长尾协作

### 核心原理

GRPO 回答长度不同。生成尾部，一部分 TP 组已经处理完自己的请求，另一些组仍在 decode 长回答。Idea1 将**空闲 die 协作、KV head 布局与状态迁移**作为一个整体：为长尾 attention 借用同一六 die 域内的空闲 TP2 组，同时保留 Q/KV head 的对应关系，让新组能够继续使用已有 KV 状态。

六 die 是**资源协作域**，不是要求模型采用 TP6。Qwen3 的 8 个 KV head 不能平均分成 TP6；本实验将六 die 分为 3 个 TP2 组，并在协作时让其中两个组组成 TP4 attention。FFN 仍由源 TP2 组执行。每条轨迹仍由原 trace 驱动，协作不能改变请求数量与完成条件。

### 执行步骤

1. **正常生成**：27 个 TP2 副本按 FIFO 处理各自请求，prefill 后进入 decode；系统记录当前活跃请求、上下文长度、完成历史与空闲组。
2. **选择介入**：当同域有完整空闲 TP2 组，且源组处于可以切换的 decode 安全点时，控制器根据已完成请求的历史长度和当前可观察状态，估算剩余协作机会及收益；不使用未来 EOS 选择迁移。
3. **估算净收益**：比较 attention 并行节省的时间，与权重/KV 传输、本地读写、打包解包、逐层激活通信、归约和新增 KV 写入的成本；只有预测净收益超过阈值才介入。
4. **搬运并协作**：按 Q/KV head 组将 helper 所需的 attention 权重和已有 KV 从源 TP2 组传到 helper TP2 组；四个 rank 同步后执行 TP4 attention。共享同一 KV head 的 query heads 按组布局，减少模型中的重复 KV 读取。
5. **持续执行并释放**：协作期间新增 KV 归属对应的源/helper lane；源组继续执行 FFN。租约在请求完成后释放，统计完成和状态生命周期。

当前控制器以 16 个 decode step 为安全点检查间隔，并使用已完成请求的历史条件长度估算；它是启发式调度，并未证明全局最优。所谓 KV 复用不是“免费发送”或“保留所有旧数据不计成本”：本轮明确计入源/目标读写、流式打包与解包、P2P、激活传输、归约和声明的 KV 增量写入。它们在事件成本模型中表示，尚未执行真实 KV 张量页搬运。

|---|---:|---:|---:|---:|

### 主要阶段耗时

| 模型 | H0 baseline 生成 / s | Idea1 生成 / s | 生成时间降低 | Idea1 训练 / s | Idea1 old + reference / s |
|---|---:|---:|---:|---:|---:|
| 4B | 107.966 | **53.217** | 50.71% | 37.107 | 17.245 |
| 8B | 162.434 | **103.937** | 36.01% | 55.318 | 27.640 |
| 14B | 219.219 | **156.099** | 28.79% | 87.803 | 41.538 |

本次 Idea1 在三档模型的晶圆对照中均减少生成和整步时间；但仅 4B 的整步低于原 GPU baseline，8B 和 14B 分别高 4.76% 和 9.54%。两个模型没有达到“最终低于 GPU”的目标，需继续优化，不能把结果改写成已经胜出。

结果体现当前融合实现的**整体效果**：包括 GQA/KV 局部访问布局与动态协作。晶圆 baseline 沿用原 KV 访问成本模式，Idea1 使用面向协作的 GQA 局部复用假设，因此表中差值不能全部单独归因于调度。GPU 与晶圆也采用不同的已声明切分和并发设置，这些设置是对照条件的一部分。

## 5. 剩余瓶颈与后续优化

**第一，8B/14B 生成阶段仍是主要耗时。** Idea1 生成分别占其 step 的 55.6% 和 54.6%。与 GPU baseline 的生成时间 89.13 s、120.81 s 相比，分别仍高约 14.81 s 和 35.29 s。TP2、较小并发、请求长尾及协作介入成本都可能影响这一差距；目前还没有将差额逐项归因到这些因素的独立测量。

**第二，已完成资源如何接续后续工作尚未解决。** 当前 Idea1 的空闲 TP2 组只能按条件帮助生成，生成与训练没有重叠。原始 idea 中“已完成资源在满足 GRPO 数据、奖励和策略版本依赖后开始后续计算”的部分尚未与当前 KV 协作融合。后续可以先记录每个 die/组的就绪、计算、通信与空闲时间，再判断何时帮助长尾、何时处理已完成组；同一资源和链路的竞争、状态准备与数据传输必须计入。

**第三，54 die 的切分仍有优化空间。** 本轮为了能均匀覆盖 54 die，采用 27 个 TP2 组，且协作仅在六 die 域内；这不是经过完整搜索的最优策略。可在模型合法性和容量约束下，探索不同域内任务放置、协作伙伴及训练/推理组织；不能简单设 TP6，因为当前三档模型的 KV head 不能均分成 6 份。

**第四，14B 容量和 reference 状态管理影响策略选择。** microbatch 1 和并发 16 是本轮满足容量上界的设置；reference 重建会消耗互联与本地读写。后续可围绕状态布局、训练/推理切分转换和通信调度，评估是否能在不超过 64 GB/die 的条件下提高并发或降低阶段时间。

**第五，硬件配置探索应与主实验分开。** H0 是当前与 GPU 近似算力对齐的主配置。48 die、96 GB/die 的 Case 4 已另行实验，作为硬件候选而非 H0；后续比较 H1/H2/H0/H3 时，应一起记录计算、DRAM 容量/带宽、D2D 和阵列布局，并区分固定预算的架构比较与单参数敏感性分析。

## 6. 结果验证与复现入口

- 三档 Idea1 各完成 1536 条轨迹；`audit-h0.json` 检查源/目标同域、KV head 覆盖、迁移与释放对应、上下文演化、容量上界、输入和源码哈希。baseline 九阶段、54 rank、6×9 网络和双方二进制一致性已检查。
- 14B reference 阶段确认执行两个 27 rank ALL_GATHER；阶段内存占用是声明的容量上界和状态生命周期模型，而非实体晶圆的内存实测。
- test1 本身参与过方案开发，本轮没有完成 54 die 的独立 test2–test4 全量结果。论文中可报告本表为**所声明模型和 trace 下的模拟结果**，并保留硬件、切分及状态管理假设。
